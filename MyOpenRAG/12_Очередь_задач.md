# Очередь задач

## 1. Что это

Система фоновой обработки загрузок: TaskService хранит задачи по пользователям (task_id → UploadTask), каждая задача содержит список FileTask. Обработка выполняется асинхронно с ограничением параллелизма (семафор по MAX_WORKERS); статусы и результаты доступны через API /tasks.

## 2. Зачем используется

- Не блокировать HTTP-ответ при загрузке больших файлов или папок.
- Повторные попытки и таймауты на уровне одного файла (ingestion_timeout).
- Единообразная модель для файлов, URL и коннекторов (custom processor).

## 3. Как работает

### Task queue

- Хранилище: self.task_store в TaskService — dict[user_id, dict[task_id, UploadTask]]. AnonymousUser получает стабильный user_id для хранения. Задачи создаются create_langflow_upload_task, create_custom_task и т.д.; возвращается task_id (UUID). Обработка запускается в фоне (asyncio.create_task), не блокирует создание задачи.

### Task status

- UploadTask: status (TaskStatus: PENDING, RUNNING, COMPLETED, FAILED), total_files, processed_files, successful_files, failed_files, file_tasks (dict path/item_id → FileTask). FileTask: status, result, error, retry_count, created_at, updated_at, filename. При опросе GET /tasks/{task_id} возвращаются эти поля.

### Retry

- На уровне процесса обработки одного файла: при временных ошибках (например OpenSearch) процессор может использовать повторные попытки (в TaskProcessor check_document_exists, check_filename_exists — max_retries с exponential backoff). Повторная постановка всей задачи в очередь в коде не реализована; при FAILED клиент может повторить загрузку.

### Таймаут

- IngestionTimeoutError: обёртка _process_with_timeout в TaskService ограничивает время обработки одного элемента (ingestion_timeout, по умолчанию INGESTION_TIMEOUT секунд). При превышении FileTask переводится в FAILED с соответствующим error.

### Очистка

- Периодическая очистка старых завершённых/проваленных задач: _periodic_cleanup (интервал CLEANUP_INTERVAL_SECONDS, 2 часа), вызывает cleanup_old_tasks. Запуск планировщика: start_cleanup_scheduler при старте приложения.

## 4. Где используется в системе

- api/router.py — после создания temp файлов вызывается task_service.create_langflow_upload_task, возврат task_id в 202.
- api/tasks.py — task_status, all_tasks, cancel_task.
- services/task_service.py — create_*_task, create_custom_task, _process_with_timeout, _periodic_cleanup, cleanup_old_tasks.
- models/tasks.py — UploadTask, FileTask, TaskStatus.
- models/processors.py — процессоры обновляют FileTask и счётчики UploadTask.
